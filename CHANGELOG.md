# Changelog

What changed in behaviour, in the order it shipped. Dates are publish dates from the registry.

## 0.3.1 — 2026-10-01

- **Profiles are advertised only when they can do something.** `mcode_profiles` and the `profile` argument appear only when the server has been pointed at a profile or one exists on disk. On a machine with neither — everyone on a MiniMax Code that has never heard of a profile — the tool list and every argument schema are byte-for-byte what they were in 0.2.0, verified by diffing `tools/list` against that release: no new tool, no new argument, and no argument that can only fail. Recomputed per `tools/list`, so signing a profile in while the server is already running makes it appear without a restart.
- **A `profile` argument that arrives anyway is still honoured.** Hiding it from the schema says what this machine can do; it is not a vote on whether the caller knows better.
- **`--profile` is never emitted without a name.** The argv builder treats anything that is not a non-empty string as "no profile". A bare `--profile` would make mcode read the *next* flag as the profile name, turning a plan that somehow lacked the field into a baffling `Invalid profile name --permission` instead of a normal run.

## 0.3.0 — 2026-10-01

- **Named auth profiles.** `profile` on `mcode`, `mcode_reply`, `mcode_models`, `mcode_context` and `mcode_history` selects a MiniMax Code account — its own credentials, sessions and settings in `~/.minimax-<name>`. The flag is mcode's own `--profile <name>`, and this server resolves its paths with mcode's own arithmetic, so a run and the transcript read back afterwards cannot disagree about which account they used. Requires a MiniMax Code with profile support (their `feat/auth-profiles` line, 0.6.0-era); without one, naming a profile fails with mcode's own unknown-option error and the default path is untouched.
- **The server's default profile is `MCODE_MCP_PROFILE`**, falling back to mcode's `MINIMAX_PROFILE`. The resolved value is pinned into every spawned mcode's environment, so a `MINIMAX_PROFILE` inherited from the server's own shell can no longer send runs to an account the server is not reading from. A malformed value makes the server refuse to start rather than quietly run on the default account.
- **A session keeps the profile it started under, and a reply may not move it.** `mcode_reply` resumes in the same account without being told and refuses a different `profile` outright, because a session id only names a conversation inside one account. A default-profile session stays on the default account even after `MCODE_MCP_PROFILE` changes, and a reply that failed still records the account it chose. `mcode_history` and `mcode_context` may read across accounts, since those are reads: `mcode_history` reports the profile it read and refuses a cursor issued for another one.
- **`mcode_sessions` shows the profile per row**, and only when it is not the default account — so the common listing is unchanged, but a listing that mixes accounts now says which is which. A row whose stored profile name is unusable degrades to itself rather than failing the call, since the listing is how a session id is found in the first place.
- **Credential state is reported honestly.** Both kinds are recognised: OAuth (`auth/**/auth.json`) and a MiniMax Token Plan API key (a `minimax_api.apiKey` in `config.yaml`), because calling a working API-key profile "signed out" would send the agent away from a usable account. The key check is scoped to that block, so another provider's `options.apiKey` is not mistaken for one, and a live credential outranks a pending authorization, so a token being refreshed is not reported as needing a sign-in.
- **The installer directory is not a profile.** `~/.minimax-code` shares the name prefix, and one definition of "this is a profile" — a directory actually holding a data directory's contents — is used by both the listing and the run guard, so `profile: "code"` cannot pass the guard into the installation directory. A mistyped `profile` is refused before anything starts rather than creating an empty account, and a session record whose stored name is unusable is refused rather than adopted for the server's default account.
- **`mcode_profiles` lists the accounts on this machine** and which is the default, with each one's credential state. A filesystem walk, so it starts no process and works on a build without profile support — at the cost of copying mcode's credential layout, which is the one thing in this feature that is not pure pass-through. A directory holding nothing is not listed, so unlike `mcode profile list` a profile is not shown until it holds data.
- **Names are validated, not sanitised.** 1–64 letters, numbers, dots, underscores or hyphens, starting and ending alphanumeric — a name becomes a directory segment under your home, so `../../etc` is refused. `default` means the default profile rather than a second, invisible `~/.minimax-default` account.
- **An answer from a non-default profile carries `[profile: <name>]`** in its prefix; a progress line names it too.
- **A profile that exists only in the legacy `~/.mavis-<name>` layout is used as mcode would use it**, resolved in one place so the run guard, the transcript lookup, the config path and the listing cannot disagree about where that account lives.
- **A relative `MINIMAX_DATA_DIR` / `MAVIS_DATA_DIR` is resolved against the server's cwd and handed to mcode in that form.** Before, the server resolved it one way and each spawned mcode resolved it against the task's own cwd, so the run and the read-back could land in different directories.
- **Unchanged, deliberately:** `MINIMAX_DATA_DIR` / `MAVIS_DATA_DIR` still outrank the profile, exactly as in mcode, and `MCODE_MCP_MINIMAX_CONFIG` stays a single path with no profile indirection — combining it with a named profile is refused rather than silently editing a file the run does not read. `mcode_profiles` warns when a redirected data directory is collapsing every profile onto one store.

## 0.2.0 — 2026-10-01

- **The installer launcher is found automatically.** `mcode` is resolved as `MCODE_MCP_BIN`, then `<prefix>/bin/mcode` (`$MCODE_INSTALL_DIR`, default `~/.minimax-code`), then `mcode` on `PATH`. A stale global `mcode` earlier on `PATH` no longer wins over the installed one.
- **Removed `MCODE_MCP_WRAP`.** The launcher pins the right Node itself; a command prefix in front of a shell launcher made Node parse `#!/bin/sh` as JavaScript. Point `MCODE_MCP_BIN` at the launcher instead.
- **One data directory for everything.** The config window patch now resolves `MINIMAX_DATA_DIR`, then `MAVIS_DATA_DIR`, then `~/.minimax` exactly like session lookup; before, it ignored `MAVIS_DATA_DIR` and `~` paths.
- Verified against MiniMax Code 0.5.9.

## 0.1.0 — 2026-09-29

First public release. Adapter over the installed MiniMax Code CLI (`mcode` / `@minimax-ai/code`), developed and verified against 0.5.8. Not MiniMax M3 in Pi, not `mmx-cli`.

- **ACP is the default transport.** `mcode acp` unless the call (or `MCODE_MCP_TRANSPORT`) asks for `print` (`mcode exec --output-format stream-json`). A running ACP turn can be `abort`/`steer` via `session/cancel`; print has no mid-run channel.
- **`follow_up` is an honest error.** MiniMax Code ACP does not document a mid-turn queue. Use `abort`/`steer` on a live ACP turn, or `mcode_reply` after it finishes.
- **A killed run is resumable.** Timeout, cancel and non-zero exit still return `[session: <id>]`. Resume with `mcode_reply`. There is no server-wide default deadline.
- **Every answer names the run.** `[session: <id>]` and `[session-key: mcode:<id>]`. With a `progressToken`, the server also sends `mcode started · mcode:<id> · cwd=…` when the session id is known.
- **Last transport is remembered.** `mcode_reply` without `transport` resumes on the same wire. `mcode_send` / `mcode_running` do not blame print after an ACP turn; print is mentioned only when that session last ran as print.
- **`mcode_history` reads a session without prompting it.** Native `messages.jsonl` at `<dataDir>/v2/sessions/YYYY/MM/DD/<time>-session_<b64(id)>/messages.jsonl` (`MINIMAX_DATA_DIR` / `MAVIS_DATA_DIR` / `~/.minimax`). User / assistant / tool; thinking and image binaries omitted. Opaque byte-offset cursor. Does not take the session lock. `state` is `active` only while this process has the ACP turn; otherwise `unknown`.
- **`mcode_sessions` lists recovery rows** including remembered transport and the transcript path when the jsonl exists.
- **ACP model selection works.** `mcode acp` does not accept `provider/model` as a `session/set_config_option` value — it takes opaque `m:<provider>:<model>:u|v:<variant>` strings and rejects everything else with `Invalid model config value`, so naming a model used to fail on every ACP run. The adapter now reads the `model` select out of the `configOptions` that `session/new` and `session/load` already return and sends the advertised value verbatim, per upstream's guidance that ACP option values are opaque. Callers may pass `provider/model` or `provider/model#variant`; without a `#variant` the model's currently selected variant is kept. A model that was never advertised is refused with the list of what is.
- **`mcode_models` reads the real catalog.** It used `mcode provider list --json`, which describes configured credentials and reports an empty `models` array for every provider under a Token Plan login — so it could not answer the question it exists for. It now reads the session catalog, and shows the current selection in the printable `provider/model#variant` form that `--model` on print accepts.
- **`mcode_context` reads a session's budget.** Opens the session, asks mcode for its own `/context` report, closes again: total window, tokens used, percentage, compaction state, and the per-component breakdown. Read-only, runs no task, denies permission requests rather than granting them, and says plainly when a session has not completed a turn and so has no snapshot.
- **`context_window` works on `print` and is refused on `acp`.** Measured on 0.5.8 rather than assumed: the ACP session selection is built from the advertised model value and carries provider, model and variant but no context limit, so the turn falls back to `defaultModelContextWindow` however the shared config is written — asking for 512000 with an explicit model and no mid-turn rollback still reported 1,000,000. `mcode acp` has no `--config` and the config path cannot be redirected without moving the whole data directory, so requesting it there is an error naming `print`, and nothing is written. `print` passes a private `--config` copy and verifiably takes effect. `MCODE_MCP_ALLOW_ACP_CONTEXT_WINDOW=1` re-enables the shared-config edit as an escape hatch. Upstream selection over ACP is requested in [minimax-code#384](https://github.com/MiniMax-AI/minimax-code/issues/384).
- **The config edit cannot corrupt the file.** It edits the user's own `config.yaml` as text, with no YAML library. Only the value is replaced, so indentation, key quoting, trailing comments and each line's own terminator survive; a form it does not fully own — an inline `minimaxModelContextLimits: {…}`, a scalar — is refused with an explanation rather than appended to, since appending leaves a duplicate key and mcode then rejects the file. Writes go through a temp file and a rename, following symlinks. A refused edit is reported as a normal tool error, not as an internal error with a stack trace.
- **Several mcode-mcp instances can share one config.** Every agent session brings up its own, and a promise chain only serialises calls inside one process. The read-modify-write runs under a cross-process lock whose staleness is "the owning process is gone" rather than an age, since it is held for the whole of a turn; each holder carries a token so `release` can never unlock someone else; waiting is `await`, so the server keeps serving other calls, progress and cancellation. A sidecar records the owning pid and time, so another instance's start will not disturb a run in flight and a crashed run is repaired on the next start.
- **A cold `mcode acp` start is slow, and the handshake budget allows for it.** Measured 3.6-21.8s for the `initialize` handshake alone, against a 15s default that failed intermittently. `MCODE_MCP_INIT_TIMEOUT_MS` now defaults to 60s for the run path, `MCODE_MCP_MODELS_TIMEOUT_MS` and `MCODE_MCP_CONTEXT_TIMEOUT_MS` to 120s.
- The readiness poll after spawn is cancelled when the process settles instead of rescheduling itself forever.
- Tools: `mcode`, `mcode_reply`, `mcode_models`, `mcode_context`, `mcode_send`, `mcode_running`, `mcode_sessions`, `mcode_history`. Each declares MCP annotations.
- Env vars: `MCODE_MCP_BIN`, `MCODE_MCP_WRAP`, `MCODE_MCP_STATE`, `MCODE_MCP_MODEL`, `MCODE_MCP_PERMISSION`, `MCODE_MCP_TRANSPORT`, `MCODE_MCP_TIMEOUT_MS`, `MCODE_MCP_MAX_TIMEOUT_MS`, `MCODE_MCP_KILL_GRACE_MS`, `MCODE_MCP_INTERRUPT_GRACE_MS`, `MCODE_MCP_INIT_TIMEOUT_MS`, `MCODE_MCP_MODELS_TIMEOUT_MS`, `MCODE_MCP_CONTEXT_TIMEOUT_MS`, `MCODE_MCP_MAX_CONCURRENT`, `MCODE_MCP_MAX_SESSIONS`, `MCODE_MCP_MAX_OUTPUT`, `MCODE_MCP_MAX_CAPTURE`, `MCODE_MCP_STDERR_LIMIT`, `MCODE_MCP_STDERR_KEEP_EVENTS`, `MCODE_MCP_MINIMAX_CONFIG`, `MCODE_MCP_ALLOW_ACP_CONTEXT_WINDOW`.
- Unsupported (error, not a fake flag): `follow_up`, `effort`, `allowed_tools`, `system_prompt_append`, `permission=ask`, `permission=off` on ACP, `mode`/`thinking_effort` on print, `context_window` on ACP.
